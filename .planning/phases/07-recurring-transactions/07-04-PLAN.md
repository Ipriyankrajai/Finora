**1. Add procedures to `packages/api/src/routers/recurring.ts`:**

Add the following procedures to the existing `recurringRouter`:

- **`pause`**: protectedProcedure mutation with input `z.object({ id: z.string().cuid() })`.
  1. Verify ownership (find rule, check userId matches session)
  2. If already PAUSED, throw BAD_REQUEST "Rule is already paused"
  3. Update rule: set `status: "PAUSED"`
  4. Return updated rule

- **`resume`**: protectedProcedure mutation with input `z.object({ id: z.string().cuid() })`.
  1. Verify ownership
  2. If already ACTIVE, throw BAD_REQUEST "Rule is already active"
  3. **Critical:** Reset `nextOccurrenceDate` to today (or the next valid date if today doesn't match the frequency pattern). Use `computeNextOccurrence` to calculate: if the rule is DAILY, set to today; if WEEKLY, find the next matching dayOfWeek from today; if MONTHLY, find the next matching dayOfMonth from today. The simplest correct approach: set `nextOccurrenceDate` to `new Date()` (start of today), and let the generation engine pick it up on its next run. The engine's loop will handle advancing to the correct date.
  4. Update rule: set `status: "ACTIVE"`, `nextOccurrenceDate: resetDate`
  5. Return updated rule
  6. **Why reset to today:** Per CONTEXT.md and RESEARCH.md pitfall #3, do NOT backfill missed occurrences during the paused period. Resetting to today prevents a flood of catch-up transactions.

- **`skipOccurrence`**: protectedProcedure mutation with input `z.object({ ruleId: z.string().cuid(), scheduledDate: z.coerce.date() })`.
  1. Verify ownership of the rule
  2. Upsert a RecurringOccurrence with status "SKIPPED" for this ruleId + scheduledDate combination:
     ```
     db.recurringOccurrence.upsert({
       where: { ruleId_scheduledDate: { ruleId, scheduledDate } },
       create: { ruleId, scheduledDate, status: "SKIPPED" },
       update: { status: "SKIPPED" },
     })
     ```
  3. If this occurrence had a linked transaction (status was GENERATED), the transaction remains but the occurrence is marked as skipped. The user can separately delete the transaction if desired.
  4. Return `{ success: true }`

- **`upcomingOccurrences`**: protectedProcedure query with input `z.object({ ruleId: z.string().cuid(), count: z.number().int().min(1).max(10).default(5) })`.
  1. Verify ownership
  2. Starting from the rule's `nextOccurrenceDate`, compute the next N occurrence dates using `computeNextOccurrence` in a loop. Respect end conditions.
  3. For each computed date, check if a RecurringOccurrence already exists (pre-skipped).
  4. Return array of `{ scheduledDate: Date, status: "upcoming" | "skipped" }`.
  This allows the UI to show upcoming occurrences and let users pre-skip them.

**2. Add hooks to `apps/web/src/hooks/use-recurring.ts`:**

Add and export:

- `usePauseRecurringRule()`: Mutation hook. On success: toast "Rule paused", invalidate recurring.list. On error: toast error.

- `useResumeRecurringRule()`: Mutation hook. On success: toast "Rule resumed", invalidate recurring.list. On error: toast error.

- `useSkipOccurrence()`: Mutation hook. On success: toast "Occurrence skipped", invalidate recurring.list and recurring.getById. On error: toast error.

- `useUpcomingOccurrences(ruleId: string)`: Query hook calling `trpc.recurring.upcomingOccurrences.queryOptions({ ruleId })`. Returns `{ occurrences, isLoading }`. Only enable when ruleId is provided.
